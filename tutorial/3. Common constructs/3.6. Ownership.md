## Ownership

Say we have the following code:

```cpp
using Standard::Text;

void DoSomething(String thing)
{
    Console::WriteLine(ref thing);
}

int main()
{
    String input = Console::ReadLine();
    DoSomething(input);
    DoSomething(input);
    return 0;
}
```

If you have a C++ or Rust background, you might think this is strange, but for different reasons.

Yes, String manages heap data, and has a destructor. Thus, in C++, code like this might be _very_ dangerous. It might produce a shallow copy, meaning the copied `String` would still have pointers to the heap data. When both the calle's copy and your copy go out of scope, you would get a double-free, and most likely a fun segfault, but it depends.

> `std::string` has a copy constuctor in C++, so in reality that code would be safe.

In Rust, code like this would simply not compile, since a non-copyable owning value would move into the first `DoSomething()` call and could not be used for the second call.

In G♭, types with a user-written destructor need an explicit copy constructor to support copying. `String` defines one. An aggregate without a custom destructor can use a synthesized memberwise copy when all its members are copyable. So this copies the string data on the heap as well, which could be slow.

G♭ makes moving explicit. If you want to call DoSomething once without copying the heap data, you can move ownership instead:

```cpp
int main()
{
    String input = Console::ReadLine();
    DoSomething(move input);
    DoSomething(move input);
    return 0;
}
```

Except this code doesn't compile.

That's because after the first `DoSomething()` call, we have moved ownership of `input`, and the compiler treats it as uninitialized.

If we initialize it again, we can reuse the stack storage:

```cpp
int main()
{
    String input = Console::ReadLine();
    DoSomething(move input);
    input = Console::ReadLine();
    DoSomething(move input);
    return 0;
}
```

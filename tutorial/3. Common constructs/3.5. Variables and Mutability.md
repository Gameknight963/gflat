# Variables and mutability

Say we have the following program:

```cpp
using Standard::Text;

int main()
{
    Console::WriteLine(Console::ReadLine().Data);
    return 0;
}
```

This will print back whatever the user inputs.

But what if we want to print it _twice?_

```cpp
using Standard::Text;

int main()
{
    Console::WriteLine(Console::ReadLine().Data);
    Console::WriteLine(Console::ReadLine().Data);
    return 0;
}
```

No, this just asks the user to input twice...

We must store the input. To do this we may use a local variable:

```cpp
using Standard::Text;

int main()
{
    String input = Console::ReadLine();
    Console::WriteLine(ref input);
    Console::WriteLine(ref input);
    return 0;
}
```

Let's unpack what's going on here in more detail:

```cpp
String input = Console::ReadLine();
```

This assigns the returned value of `ReadLine()` to a local named `input` of type `String`.

We'll discuss types in greater detail later, but all that matters in this case is that nothing else but a `String` may be assigned to that local.

We can also leave the value _uninitialized_ like so:

```cpp
String input;
```

Now, the compiler will prevent you from using it until you have initialized it on every branch.

```cpp
Console::WriteLine(ref input);
```

This gives WriteLine a _reference_ of the value stored in `input`. Passing with `ref` borrows the existing storage instead of copying the owning value. It does not transfer ownership to the callee. Raw pointer operations can still bypass this contract.

Passing by `ref` means the calle might modify your value though. Let's see what `WriteLine()` does with it:

```cpp
void WriteLine(ref immutable(Standard::Text::String) message)
{
    Write(message.Data, message.Length);
    WriteLine();
}
```

## Mutability.

When a variable is _readonly_, once a value is bound to a name, you can’t change that value.

```cpp
using Standard::Text;

int main()
{
    readonly String input = Console::ReadLine();
    Console::WriteLine(readonly ref input);
    Console::WriteLine(readonly ref input);
    return 0;
}
```

When a variable is readonly, once a value is bound to a name, you can’t reassign that value.

An ordinary `ref input` already preserves the variable's readonly protection. Writing `readonly ref input` makes that restriction explicit at the call site. Either form cannot bind to a parameter that requires a mutable reference.

This behaves exactly the same as the original program, but is better for several reasons:

 - `readonly` prevents accidental data modification.
 - `readonly` improves code readability by expressing intent.

Note that although the value itself cannot be changed (including any fields), any pointer members on the value can be dereferenced and their corresponding memory changed. In other words, this is a "shallow" readonly.

Since we don't intend to modify the value at ALL here, we can use a "deep" readonly: `immutable`.

```cpp
using Standard::Text;

int main()
{
    immutable String input = Console::ReadLine();
    Console::WriteLine(immutable ref input);
    Console::WriteLine(immutable ref input);
    return 0;
}
```

We can pass an `immutable ref` since `WriteLine()` is defined to accept one:

```cpp
void WriteLine(ref immutable(Standard::Text::String) message)
{
    Write(message.Data, message.Length);
    WriteLine();
}
```

We can also pass a mutable reference if we want, since a mutable value can be borrowed through a readonly or immutable reference.

If your functions use references, use `readonly` or `immutable` references when the function does not need to modify the borrowed storage. This prevents the caller from being forced to use a mutable value.

This definition uses the function-like form of `immutable`. We can use it in our code as well:

```cpp
using Standard::Text;

int main()
{
    immutable(String) input = Console::ReadLine();
    Console::WriteLine(immutable ref input);
    Console::WriteLine(immutable ref input);
    return 0;
}
```

It means exactly the same thing in this case. It becomes most useful when we start dealing with pointers in section 4.2.

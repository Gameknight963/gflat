# Allocating and Freeing Memory

Sometimes, you might want an array of a dynamic size, or to return a unique pointer on each function call.

<details>
<summary>The stack and the heap</summary>

We can do that by allocating memory on the heap.

Many programming languages don’t require you to think about the stack and the heap very often. But in a systems programming language like G♭, whether something is on the stack or the heap affects what you do with that memory.

Both the stack and the heap are "memory," but they are structured in different ways.

Stack frames organize storage around function calls. A function can reserve a frame for several locals at once, and some locals stay in CPU registers rather than on the stack. `push` and `pop` are useful parts of the machine's stack machinery, but a local declaration does not necessarily produce either instruction.

A heap allocator, such as the one behind `Memory::Allocate`, manages blocks with independent lifetimes. It often reuses memory it already has and asks the operating system for more only when needed. There is no fixed rule that places the heap above the stack.

Stack storage is usually cheap to reserve and release with a function's frame. Heap allocation also needs to track free blocks, alignment, and independent lifetimes, which can make it more expensive.

G♭'s fixed-size arrays require a compile-time length. This is a language rule, not an inherent limit of stacks. Other mechanisms can choose a stack allocation's size at runtime. Neither a fixed stack buffer nor a fixed heap block automatically grows when you write past it. A `Vector` can allocate a larger block and move its elements there when needed.

</details>
<br>

Take this example for instance:

Filename: static_storage.gf
```cpp
int* GetPointer()
{
    static int number = 4;
    return &number;
}

int main()
{
    int* ptr1 = GetPointer();
    *ptr1 = 777;
    int* ptr2 = GetPointer();
    Console::WriteLine(*ptr1);
    Console::WriteLine(*ptr2);
    return 0;
}
```

```
$ gflat static_storage.gf --run
777
777
```

The pointee of `ptr2` changed when we dereferenced `ptr1`! That's because we returned the address of the same static variable, so they point to the same location in memory.

To fix this, we can _allocate memory_ on the heap. That can be done with `Memory::Allocate()`. It returns `void*?`, so we need to cast it before using it:

```cpp
int*? GetPointer()
{
    return (int*?)Memory::Allocate((nuint)sizeof(int));
}

int main()
{
    int*? ptr1 = GetPointer();
    if (ptr1 == null) return 1;
    *ptr1 = 777;
    int*? ptr2 = GetPointer();
    if (ptr2 == null)
    {
        Memory::Free(ptr1);
        return 1;
    }
    *ptr2 = 0;
    Console::WriteLine(*ptr1);
    Console::WriteLine(*ptr2);
    return 0;
}
```

```
$ gflat allocation.gf --run
777
0
```

The blocks are independent, so writing through `ptr1` does not change `*ptr2`. We explicitly initialized both values. `Allocate()` does not initialize the bytes it returns.

`Allocate()` takes a size in bytes as a `nuint`. The cast changes `void*?` to `int*?` and preserves nullability. A null result means allocation failed, so we check each pointer before dereferencing it.

Later, we'll learn about exceptions, which can make code like this less repetitive.

This memory is also...

## Leaking.

Any memory allocated MUST be freed with `Memory::Free()`! Otherwise you get a _memory leak_: your program uses more and more memory until bad things happen (depending on your OS).

In this case, it's technically fine. We make two allocations before immediately exiting. The exit means the OS cleans any memory we allocated anyway.

But it's good practice to free the memory regardless:

```cpp
int*? GetPointer()
{
    return (int*?)Memory::Allocate((nuint)sizeof(int));
}

int main()
{
    int*? ptr1 = GetPointer();
    if (ptr1 == null) return 1;
    *ptr1 = 777;
    int*? ptr2 = GetPointer();
    if (ptr2 == null)
    {
        Memory::Free(ptr1);
        return 1;
    }
    *ptr2 = 0;
    Console::WriteLine(*ptr1);
    Console::WriteLine(*ptr2);
    Memory::Free(ptr1);
    Memory::Free(ptr2);
    return 0;
}
```

After `Free`, the corresponding pointer dangles. Dereferencing it is undefined behavior, whether or not the program happens to crash.
